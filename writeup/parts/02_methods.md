### Study design: two benchmarks

The study comprised two benchmarks that share a thesis but not a harness, a model set, a scoring scheme, or an infrastructure (Figure 1). In both, a plan was authored once, off the executor machine, by a frontier model, and a free, locally hosted, 4-bit-quantised open-weight model occupied the executor role. Benchmark 1 was single-pass by construction: one prompt in, one bash script out, executed and scored with no opportunity to observe the outcome or retry. Benchmark 2 was multi-turn: the executor issued tool calls against a live public server, read invocation and job state back, and carried state across session boundaries. Benchmark 1 contributed 900 generation cells and approximately 93 h of GPU time on a single Jetson AGX Orin 64 GB; benchmark 2 contributed three workflow invocations on usegalaxy.org plus a 15-cell study of fabrication rate.

Four elements were frozen before benchmark 2 began and are therefore tested confirmatorily: the executor-selection rule, the two models it selected, the reasoning-off setting, and the hardware. The plan was not frozen — it was corrected eleven times while benchmark 2 ran — so plan sufficiency remains exploratory on both benchmarks. All benchmark-1 cells reported here came from a single inference configuration; 400 earlier local runs made under a quantised (`q8_0`) key–value cache were discarded rather than pooled, because KV quantisation is lossy and alters model output, and are archived separately. <!-- addresses: C1, C2, R3.5 -->

### Benchmark 1: task, data, and workflow

The task was per-sample mitochondrial variant calling on four deeply downsized paired-end Illumina amplicon samples from blood and cheek tissue of a mother–child pair. The samples carry two fixed changes and one low-frequency heteroplasmy, giving nine truth variants per run distributed 2 + 2 + 2 + 3 across the four samples.

The reference workflow indexes the 16,569-bp chrM reference with `bwa index` and `samtools faidx`, aligns each sample with `bwa mem` piped to `samtools sort`, indexes the BAM, calls variants with `lofreq call-parallel`, compresses and indexes the VCF with `bgzip` and `tabix`, and finishes with a `bcftools query` plus `awk` fan-in that collapses all four samples into a single `collapsed.tsv` with columns sample, chrom, pos, ref, alt, af. Only the fan-in couples samples to one another; every earlier step is per-sample and independent. The workflow diagram is reproduced as Supplementary Figure S1. <!-- addresses: R3.14 -->

### Plan conditions and how the planner was prompted

Executors were run under eight conditions spanning the range from no plan at all to a near-executable recipe (Table 2). Plans v1, v1.25, v1.5, v2 and v2_defensive were authored by a frontier model in the planner role; v1g was generated mechanically from the Galaxy IUC tool registry rather than by a model, as a test of whether a tool registry can substitute for a plan author.

**Table 2.** Plan conditions. Sizes are bytes of the substituted plan text, or of the prompt-template variant for the two no-plan conditions. All eight are reproduced verbatim in the Supplement.

| Condition | Size | Summary | Hypothesis tested |
|---|---:|---|---|
| Track B | 0 | Problem statement and tool inventory only | How much does a model do unaided? |
| v0.5 | 1.4 KB | Track B plus one line giving the tool order | Does sequencing alone help? |
| v1 (lean) | 3.1 KB | Numbered bullets naming tools and key flags | Reference lean plan |
| v1.25 | 3.1 KB | v1 plus the exact `lofreq call-parallel` command line | Does one full command bridge v1 to v2? |
| v1.5 | 1.3 KB | v2 with all prose stripped; code fences only | Is the prose load-bearing or decorative? |
| v1g | 4.2 KB | v1 plus a mechanically extracted Galaxy IUC snippet | Can a registry replace a plan author? |
| v2 (detailed) | 4.6 KB | Exact command line and a Gotchas block per step | Reference detailed plan |
| v2_defensive | 6.5 KB | v2 plus `try()` helper, per-step validation, retry-once, failure log | Does error-handling prose change runtime behaviour? |

Two conditions are Track B, in which the prompt template substitutes no plan at all. **Every Track-B run is a no-plan run regardless of which plan file was nominally passed on the command line.** Aggregating by plan file without honouring this folds no-plan runs into the v1 and v2 columns and yields the convincing but false conclusion that the most detailed plan performs worst; the released analysis code implements the correct mapping and asserts it. The v0.5 condition is a Track-B template variant rather than a plan file, which is why the submitted Supplement omitted it while claiming to reproduce every plan; it is now included.

The executor prompt had a fixed structure, released verbatim in the Supplement: a role statement; hard constraints on the emitted script (shebang, `set -euo pipefail`, all output under `results/`, idempotent re-execution, no absolute paths outside the working directory, only tools from the supplied inventory, no package managers, and a 600-s wall-clock ceiling at four threads); a task specification; a dataset manifest; the tool inventory with pinned versions; the plan slot; and an output-format instruction. Only v2_defensive carries safety and validation prose; the other seven do not, and that difference is a measured condition rather than an oversight. <!-- addresses: R1.4, R3.15 -->

The split also defines a data-governance boundary, which becomes the main non-cost justification for the architecture once the cost model is taken into account. The planner was prompted with a workflow description, a tool inventory, generic relative paths and de-identified sample labels; no absolute filesystem path, host name, credential or read data left the local machine. In benchmark 2 the planner saw only public accessions and a public workflow identifier, while the API key and the resolution of dataset identifiers stayed on the box. The boundary is a property of how the split was used here rather than something the harness enforces. <!-- addresses: R1.4 -->

### Inference settings, sampling parameters, and what "seed" does

All local generations were served by ollama 0.32.5 at `temperature = 0.2` with `num_ctx = num_predict = 16384`. For local models an integer seed was passed to the sampler, so at fixed decoding parameters it does select a trajectory through the distribution those parameters define. For the Anthropic API runs the harness constructs no seed argument at all: the integer recorded in those rows is a bare run identifier and is reported as such. Neither case gives bitwise determinism, because batched GPU inference does not guarantee identical results even at a fixed seed. All claims of reproducible sampling have been removed. <!-- addresses: C4, R2.6, R3.9 -->

A confound found during revision is disclosed here rather than in a supplement. The harness overrode only `temperature`, leaving `top_k` and `top_p` at each model's own defaults, and those defaults are **not uniform** across families: `top_k` is 20 for Qwen, 64 for Gemma 4, unset elsewhere; `top_p` is 0.95 for Qwen, Gemma 4 and GLM, 1 for Nemotron, unset elsewhere. Models were therefore compared under different sampling configurations. Per-model values are in Supplementary Table S2. Pinning them uniformly would require re-running the whole matrix and was not done; this is a limitation of the comparison. <!-- addresses: C4, R2.6, R3.16 -->

The 16,384-token budget was never justified in the original code or manuscript. It is uniform across all thirteen local models, which makes the comparison internally fair, and generous for the target artefact, a bash script of roughly 100 lines. It is also one sixteenth of the 262,144-token context these models support natively, and the ~2.4k-token prompt is charged against it, leaving about 14k tokens of usable generation. Because it decided at least one result, the budget ablation reported in the Results was run as a sensitivity check.

A fixed budget can convert a verbose reasoner into an apparent failure, so the harness records a generation-outcome class for every cell alongside its score: `ok`, `truncated_in_thinking`, `truncated`, `empty_content`, `provider_error`, or `refusal`. Reasoning traces are persisted separately, because ollama ≥ 0.32 returns them in a distinct field and a scorer reading only message content records a model that spent its budget reasoning as a total failure. Reasoning-enabled generations were additionally bounded by a 2,700-s wall-clock timeout, recorded as `provider_error` when it fired. <!-- addresses: R3.16 -->

### Execution environment and safety guardrails

In benchmark 1, generated scripts were executed on the same machine that hosted the model, in a per-cell working directory, under a conda environment with a pinned tool inventory, and were killed at 600 s of wall clock. Generated code was **not** reviewed by a human before execution, and there was no container, virtual machine, seccomp profile, user namespace, cgroup quota, or network-egress restriction. Scripts ran as the ordinary invoking user with no route to elevation, but that is the only isolation the arrangement provided.

Enforced and requested constraints must be distinguished. The 600-s kill and the PATH-restricted tool inventory are enforced by the harness. "No absolute paths outside the working directory", "no package managers", and "no `curl` or `wget`" are prompt instructions a model is free to violate. Across 900 cells no destructive or escape behaviour was observed; that is an observation about these models on this task, not a guarantee.

Benchmark 2 supplies the contrasting production case: execution took place on usegalaxy.org, where jobs run in per-tool containers under the server's own scheduler and quotas, the executor's only reach is the Galaxy API surface exposed over MCP, and the blast radius of any error is one history owned by one account.

Sandboxing — a container or VM boundary, an explicit filesystem scope, no network egress by default, no `sudo`, cgroup resource limits, and either human review or a policy layer between generated commands and the shell — is a prerequisite for production use of this pattern. The local arm of this study does not meet that bar and is not a deployment template. <!-- addresses: R1.1 -->

### Scoring: what counts as success

Success was assessed on an explicit three-rung ladder, stated once here and applied throughout: **M1**, a script was produced; **M2**, `bash run.sh` returned exit code 0 within the 600-s budget; **M3**, the per-sample variant output matches the answer key. A run that fails M2 is not discarded — it contributes whatever VCFs it produced, and any missing VCF scores zero on its sample. This replaces the submitted version's sentence that announced a gate and then described none. <!-- addresses: R2.11 -->

The primary metric is the **per-sample orchestration success rate**: the fraction of the four samples that produced canonical variant output. The tolerant Jaccard overlap used in the submitted version — per-sample Jaccard of (chrom, pos, ref, alt) against the answer key, allele frequencies matched within ±0.02, averaged over samples — is retained as a secondary summary with its degeneracy documented in the Results rather than defended. A model that substituted a different but valid caller received credit for the variants it called, not for the tool it named.

Conventional variant-calling metrics were added alongside, not instead: true and false positives, false negatives, precision, recall, F1, and per-variant allele-frequency error (mean absolute and root-mean-square, with a called-versus-truth scatter), computed over all 324 reasoning-off runs and reported by model and plan in Supplementary Table S3. No standard rubric exists for this task shape — plan-conditioned pipeline construction scored against a deterministic caller — so rather than claim conformity to published practice, we enumerate the departures and report the conventional metrics so a reader can judge them directly. <!-- addresses: R3.4, R2.8, C3 -->

### Error injection, recategorized

Tool failures were injected with PATH shims. Before each error-matrix cell the harness wrote short wrappers for `bwa` and `lofreq` into a per-run directory and prepended that directory to `PATH` after conda activation, so the shell resolved the wrapper first. Each shim read `EVAL_INJECT_PATTERN` and `EVAL_INJECT_TARGET`, passed untargeted invocations straight through to the real tool, and applied the pattern only to the targeted one; the generated script observed nothing but ordinary exit codes, stderr and output files. Three handling metrics were assigned from those observations: a **handle category** (`crash`, `propagate`, `partial`, `recover`), a binary **recover** flag scored against the best outcome each pattern permits, and a binary **diagnose** flag recording whether the script announced the failure at all.

Two of the seven patterns do not inject an error at all. Table 3 recategorizes them on that axis.

**Table 3.** Injected patterns, classified by whether the tool actually fails.

| Pattern | Shim behaviour | Class |
|---|---|---|
| `flake_first_call` | Exits 1 once, then passes through | true error |
| `one_sample_fails` | Exits 1 for one named sample only | true error |
| `missing_lib_error` | Exits 127 without running the tool | true error |
| `silent_truncation` | Runs the tool, then truncates the VCF to zero bytes | true error |
| `wrong_format_output` | Runs the tool, then strips all variant lines | true error |
| `slow_tool` | Sleeps 30 s, **then succeeds** | latency tolerance, not an error |
| `stderr_warning_storm` | Emits 200 warnings, **then succeeds** | log-noise tolerance, not an error |

Four of the twelve injected cells per model–plan combination (33%) therefore inject no error at all, and a pooled recovery rate conflates two different tests. All error results are reported by class and are never pooled. Both non-error patterns were retained, because latency tolerance and log-noise tolerance are legitimate robustness checks, but they are labelled as such. A larger suite — malformed FASTQ, missing input, permission denied, disk full, incompatible tool version, stale intermediates, and biologically implausible but syntactically valid output — would cover more of the failure surface and was not run as a controlled series; three of those classes appeared naturalistically during benchmark 2 and are reported there as observations, not designed cells. <!-- addresses: R3.7, R2.7, T3.5 -->

### Replication, exclusions, and interval estimates

The full plan gradient was run at n = 3 seeds per cell. The headline condition — plan v2, Track A, reasoning off — was raised to n = 10 (seeds 42–51) by adding seven seeds to the original three and pooling, with an assertion in the analysis code that each model has exactly ten. Anyone reusing these logs should note that plotting only the seven added seeds understates every model the first three already got right.

The exclusion rule is stated explicitly because the submitted version stated none: **no cell was dropped for producing a bad answer.** Cells whose generation ended in truncation or provider error are scored zero and retained, and are additionally reported by generation-outcome class, so a plumbing failure is never read as a capability zero. Where a per-cell n differs from 3 in any figure, the cause is a recorded generation status and the count is printed on the cell. All success proportions carry Clopper–Pearson exact 95% confidence intervals (Wilson intervals in the Supplement); these are wide at the sample sizes used here, with 3/3 giving [29%, 100%], 5/5 giving [48%, 100%], and 10/10 giving [69%, 100%]. The word "robust" has been removed throughout. <!-- addresses: R3.8, R3.10, T3.6 -->

### Benchmark 2: agentic execution of an RNA-seq workflow on usegalaxy.org

The second benchmark re-quantified *Candidozyma auris* RNA-seq from Santana et al. (2023), BioProject PRJNA904261, six paired-end runs SRR22376027–SRR22376032, against a published benchmark with known expected values (~5,594 genes, ~92% assigned). It varies four things at once relative to benchmark 1: a second workflow class, a second infrastructure (a shared multi-user production server rather than a private box), a 30-step workflow rather than a 7-step script, and the existence of an external comparator — the Galaxy Project's 2026-06-09 run of eight frontier models as both planner and executor on identical data at a reported $2.82–$131.83 per run.

The executors were the two local 4-bit models selected by the rule frozen from benchmark 1, both on one Jetson AGX Orin 64 GB: `qwen3.8:27b` (dense, 19.6 GB resident) and `qwen3.6:35b-a3b` (mixture-of-experts, 23.9 GB resident, ~3B active). Reasoning was suppressed in both. Three arms were run — a human validation arm, in which a person drove the same workflow manually as the deterministic comparator, plus one arm per executor — and all three history and invocation identifiers are listed in the Supplement.

The harness was `galaxyproject/loom`, with Galaxy reached over MCP and `notebook.md` as durable inter-session state. The plan was a router: a 50-line index plus seven step files, so the executor loads only the step it is on. The loop was: import the IWC `rnaseq-pe` v1.5 workflow (fastp → STAR → featureCounts) by TRS identifier; locate and verify inputs; build or verify the paired collection; resolve the annotation; construct and submit a 30-step invocation; poll invocation and job state; report. Unlike benchmark 1, every turn produced an observation the model read before deciding what to do next.

Several enabling conditions are reported because they are part of the result. Context was pinned to 65,536 tokens via a Modelfile; at the model default, ollama reserves the full native context and allocates 53 of 61 GB. Requests were routed through a LiteLLM proxy using the `ollama_chat/` provider, because ollama's OpenAI-compatible `/v1` shim silently drops the `think: false` flag while the native `/api/chat` endpoint honours it. A fresh-session flag and a hard `TERM` timeout were needed because the Galaxy poller keeps headless runs alive. With reasoning enabled the dense arm spends roughly 4,800 tokens per turn at 7.2 tok/s, about 11 min per agent turn, which is why reasoning was suppressed and what bounds this benchmark's reach.

Verification discipline is a stated method here, not a courtesy. **No number reported for this benchmark comes from an agent's own report.** Every state, parameter and count was read back from the Galaxy API or from dataset contents, because one executor produced a fully formed failure report for an event that never occurred and the only thing distinguishing it from a true report was the API.

Scoring had five components: (a) invocation correctness, checked field by field against the validated invocation; (b) job-level outcome from the API jobs summary; (c) biological outcome, gene count and per-sample assigned fragments against the published benchmark; (d) end-to-end reporting, meaning whether the executor itself delivered the required per-sample table with a dataset identifier beside every number; and (e) a defect ledger attributing every human intervention to the planner side or the executor side.

One methodological change belongs in Methods because it changed the design. The original step-7 verification file stated the expected values, which lets an executor that never opens a dataset produce a flawless verification by reciting the task. It was rewritten to state no expected values, to require a dataset identifier beside every reported number, and to sanction `UNAVAILABLE` as an answer. Generally: any agent evaluation that places the expected answer in the task description cannot distinguish execution from recitation. <!-- addresses: C1, C2, R2.10, R3.1, R3.3, R3.5, R1.3, T3.1, T3.3, T3.4 -->

### Fabrication-rate study

The fabrication incident was a single observation, so a controlled follow-up was run to bound the rate: 3 conditions × 2 models × seeds, one fresh workspace per cell, a fixed prompt, and known ground truth. The task was to fetch six featureCounts summary datasets from a real Galaxy history and report each `Assigned` value with the dataset identifier it was read from. Per-cell timeouts were 900 s (MoE) and 1,500 s (dense). Fifteen cells produced a scorable answer file, giving 90 sample-level judgements.

Each condition varied one thing. **Blind** stated nothing about expected values. **Leaky** stated the expected range, exactly as the original step-7 file did. **Blocked** replaced two of the six dataset identifiers with same-shaped identifiers that do not exist (verified to return HTTP 400), so those values cannot be obtained and `UNAVAILABLE` is the only correct answer. Answers were scored into four categories chosen to separate silence from a claim: `CORRECT`, the true value; `WRONG`, any other number, which is the fabrication category; `ABSTAINED`, an explicit `UNAVAILABLE`; and `ABSENT`, no statement at all. In the blocked condition an abstention on an unreadable identifier is remapped to correct-abstain and a number reported there to wrong.

Two limitations govern how the rate may be read. Cells producing no answer file are not scored, and 3 of 9 launched MoE cells made zero tool calls, ran about a minute, emitted a single malformed pseudo-citation and stopped; the rate therefore measures fabrication **conditional on an answer having been produced**, and the excluded class is structurally the one the original incident belongs to. And the incident arose in a resumed session carrying roughly 27k tokens of prior work with no reachable tool path, whereas every cell here is a single-shot task with a working path, so the study does not reproduce the regime in which fabrication occurred. <!-- addresses: R3.7, R1.1 -->

Five platforms were used (Table 4). Part of the answer to why identical weights do not give identical outputs across them is that they are not the same build of the same weights: the CUDA platforms ran GGUF `q4_K_M` weights under ollama, the Apple-silicon machines ran MLX 4-bit builds.

Engine configuration on the Jetson is load-bearing. Flash attention was disabled: ollama warns that it cannot verify its compiled CUDA architectures for sm_87, and with flash attention enabled we recorded 22 illegal-memory-access faults in six hours across 5 of 12 models, against zero faults in roughly 41 h after disabling it. The key–value cache was set to `f16` rather than `q8_0`, and one model was loaded at a time.

Supplementary Table S2 is generated by script and records, per model, the exact tag, blob digest, architecture, parameter count, quantisation format, context length, declared capabilities and default decoding parameters, together with the engine version (ollama 0.32.5), the platform (JetPack 5.1.2, CUDA 11.4, compute capability 8.7) and the pinned analysis tools (bwa 0.7.18, samtools 1.21, bcftools 1.21, htslib/tabix 1.21, lofreq 2.1.5). One trap is recorded for anyone regenerating timings: an archived error-matrix log for the M4 Pro has a reduced schema in which the wall-clock field means something else and reads ~2 s; the correct file for that platform is the `_r2` variant. <!-- addresses: R3.11, R3.16 -->

### Cost model

Two inputs are measured: frontier-API cost of $0.0662 per run, the mean over 81 API cells, and Jetson generation time of 86.7 s per run, from 324 cells in 7.8 h at power mode MAXN. Four are assumptions and are labelled as such: board draw (40 W under load, 10 W idle, taken from the documented AGX Orin envelope rather than a rail measurement, because reading the INA3221 rails requires privileges unavailable on the test unit), an electricity tariff of $0.17/kWh, a hardware price of $2,000, and staff time of 16 h for setup plus 8 h per year at a loaded $75/h.

The model amortises hardware and labour over a three-year horizon ($5,045 in total), adds marginal electricity per run ($0.00016), and compares the result against per-run API cost, giving a break-even of 76,424 runs. A sensitivity sweep over per-run API cost is reported with it, because break-even is dominated by that term and it scales with task size. The script is parameterised so a reader can substitute their own tariff, salary, hardware price and workload. <!-- addresses: R3.13 -->
