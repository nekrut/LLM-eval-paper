## Discussion

### What was demonstrated and what was not

Two things were demonstrated. Given a sufficiently specified plan, free 4-bit open-weight models running on a single sub-$2,000 board acted as executors on two workflow classes and reproduced the outcomes that frontier models produced on the same tasks: once as single-pass script generation against a 7-step mtDNA variant-calling workflow, and once as a multi-turn tool-using loop that drove a 30-step community workflow on a shared production server to a gene count matching the published benchmark exactly. Three things were not demonstrated. Autonomous analysis was not: in both benchmarks the specification was authored elsewhere, and in the agentic benchmark eleven human corrections to the plan preceded any clean run. Orchestration as distinct from transcription was not: both benchmarks supply near-executable material at the detailed end of the plan gradient, and the planner comparison at matched detail that would separate the two was not run. And the substitution of iteration for plan detail was not: the bounded-repair arm across the plan gradient was not run, so benchmark 2 shows that a loop works, not how much of a plan a loop can replace. <!-- addresses: R3.preamble, C1, C2, R3.6, T3.1, T3.2, R2.10 -->

### Plan sufficiency is the engineering object

The result that recurs across both benchmarks is that the specification, not the model, separates success from failure. A newer, higher-benchmarking model did not move the plan-detail cliff: `qwen3.8:27b` and `qwen3.6:27b` are matched in parameter count, quantisation and engine and differ by one generation, and their mean scores across the gradient were 0.57 and 0.67, with the two single-column differences opposite in sign at n = 3. A defensive plan changed error handling for a frontier executor and a local executor identically. On the Galaxy workflow, eleven of the thirteen interventions needed to reach a clean run were plan defects and two were executor errors.

The practical consequence is that the artifact a laboratory should invest in, version-control and review is the plan, not the model. The plan is short, human-readable and diffable; the model is a commodity that will be replaced within months.

What makes a plan sufficient is taken from the defect ledger rather than asserted. A sufficient plan carries the exact command syntax or the exact body of every API call; names the identity of every value carried between steps, rather than saying "record the output id" where three ids exist; states the gotchas at points where a plausible action fails; specifies a validation and retry policy wherever a late failure is expensive; and states no expected answers in its verification step. The fabrication result adds a corollary: plan sufficiency governs the reporting channel as well as the execution channel. A verification step must sanction "I could not obtain this", or it will be answered anyway. <!-- addresses: R3.15, R3.2, R1.4 -->

### Where the split earns its keep once cost is off the table

The cost model withdraws the economic argument this study originally rested on. At $0.0662 per API run and a break-even of 76,424 runs, a local executor does not pay for itself on a task this small. What the planner-executor split still buys is an abstraction boundary. The planner sees a workflow description, tool names and generic paths. The executor binds the real paths, the real sample identifiers, the real directory layout and the local system metadata, and it does so on hardware the laboratory controls. Nothing that identifies a sample or a filesystem needs to cross an API boundary.

This is a policy-relevant property rather than a preference. It is what allows the pattern to be used where sample identifiers or local configuration cannot be sent to a commercial endpoint, and it holds at any run count, including run counts far below break-even. Two further non-monetary properties follow from local inference: there is no per-call metering, so an exploratory session carries no budget ceiling and no rate limit; and there is no vendor dependency, so a workflow validated today still runs after a model identifier is deprecated.

None of these three properties was measured. They are design properties of the architecture, argued here and not tested, and they are offered in that spirit. A laboratory weighing them should weigh against them the setup and maintenance labour that dominates the cost model, at $3,000 of the $5,045 three-year total. <!-- addresses: R1.4, R3.13 -->

### From a private box to a shared cluster

Benchmark 2 already supplies part of the answer to what changes in a production setting, because usegalaxy.org is one. The executor operated under an external scheduler with real queueing, per-tool containerisation, per-account isolation, and server-side provenance recorded independently of the agent. Its blast radius was a single history, and every action it could take was an API call.

That setting exposed something a private box does not. A job can fail for reasons unrelated to the model or the plan: one arm's final invocation carries an errored `bedtools` job (exit 255, a missing container path on a compute node) and one job paused behind it. Neither executor noticed that its invocation was not clean. Failure detection, not failure recovery, was the gap.

What still changes on a shared cluster was not tested: multi-user isolation of the executor process itself, credential scoping, queue-time behaviour when a polling loop outlives the session that started it, paging a human when a job fails unattended, and provenance that links a generated command to the plan revision that produced it. Three recommendations follow from the observed failure modes rather than from principle. Run the executor with a bounded tool surface and read-back verification on every state-changing call. Treat durable agent memory as a cache that must be invalidated by whatever process changes the underlying facts. And require a dataset or job identifier beside every number an agent reports. <!-- addresses: R1.3, R1.1, C2 -->

### Generalisation across workflow classes

Two of the six workflow classes in Table 1 were run. They were chosen to differ on the axes that matter for an executor: step count (7 versus 30), infrastructure (a private board versus a shared multi-user server), interface (shell commands versus API calls), and failure surface (tool exit codes versus job states). Convergence across those differences is the reason the plan-sufficiency finding is stated as a result rather than as an observation about one workflow.

Two properties are likely to transfer. The plan-sufficiency threshold is a property of specification density rather than of the biology. The failure modes of durable state and of unverified reporting are properties of the loop rather than of the analysis.

One class of property is unlikely to transfer without testing. Where a workflow requires parameter choices that depend on the data — assembly parameterisation, single-cell clustering resolution, peak-calling thresholds — there is no canonical answer for an executor to transcribe, and the model would be making a scientific judgement rather than wiring a pipeline. This study measured orchestration precisely because its two benchmark tasks contain no such judgement: the variant caller is deterministic, and the RNA-seq workflow was a published, parameterised community workflow. The boundary this sets on the claims is therefore explicit. The results support the use of local executors for binding and running pipelines. They say nothing about the use of local executors for analytical decisions. <!-- addresses: R2.4, C2, R3.3, R3.preamble -->

### Limitations

The evidentiary base is two workflow classes with one dataset each, and no perturbation series was run — no variation in depth or allele frequency, no reference swap, no tool-version change — which is what would make the accuracy metrics informative rather than degenerate by construction. Benchmark 2 is n = 1 invocation per arm, two models, no replicates and no frontier control. Nothing in it carries a confidence interval, which sits awkwardly beside a Results section that reports exact intervals everywhere else, and it is fairly read as a case study rather than an experiment.

Three gaps are conceded outright. The transcription-versus-orchestration confound is stated and not resolved: the Galaxy plan supplied a literal invocation body at the decisive step, and a human pre-built the input collection and the annotation after a harness transport fault, so two of seven steps became verification rather than construction and the "8/8 parameters correct" figure measures faithful transcription of a supplied call — the same criticism benchmark 2 was introduced to answer. The planner comparison that would resolve it, at matched detail across an expert-written plan, a second frontier planner and a documentation-assembled plan, was not run. Neither was the bounded-repair arm on benchmark 1; the harness records the logs it would need, so the accurate statement is that it was not run, not that it could not be. The expanded error-injection suite was not run as a designed matrix either: three of its classes appeared naturalistically in benchmark 2, which is an observation and not a controlled comparison, and the biologically-implausible-output probe was not implemented.

Individual results carry their own limits. The plan was corrected eleven times while benchmark 2 ran, so plan sufficiency was not tested under a frozen protocol on either benchmark. Decoding parameters other than temperature sat at per-model defaults that differ across families; they are disclosed and not controlled, and the pinned re-run was declined on cost. The reasoning penalty at a sufficient plan narrows to essentially one model, because `gpt-oss:20b` shows no v2 penalty at a generous budget, and the twelve-cell re-run that would settle it was identified and not performed. The fabrication bound of ~3.3% is conditional on an answer being produced: zero-tool-call sessions produced nothing scorable, fall outside the denominator, and are the class the original incident belongs to. "Both executors submitted a parameter-correct invocation" is true; "both executors succeeded" is not, because neither reported a single per-sample number and a human read the published values out of the Galaxy API. Board power in the cost model is a documented envelope, not a rail measurement. The economic case fails at these task sizes on the study's own numbers, and the governance rationale that replaces it is argued rather than measured.

Five limitations concern the study as an object. The two benchmarks share a thesis but not a harness, model set, scoring scheme or infrastructure. The model set was not stable: the frontier reference moved from Opus 4.7 to Opus 5, which reasons by default and is therefore not a like-for-like generational substitution and whose per-run cost and latency vary accordingly, and a new Qwen generation was added mid-study. The reasoning-versus-plan-detail result and its budget ablation were requested by no reviewer; they are reported because they test the central claim, at the cost of opening a second topic. A requested head-to-head against an existing bioinformatics agent framework was declined on scope grounds rather than answered with data. And three residual defects are disclosed rather than fixed: the plan author is a closed-API model in both benchmarks, so a laboratory that cannot use one has no evidence here about an open-weight planner; the released Galaxy plan index still names the GFF3 annotation that step 3 now forbids, the most expensive defect in the ledger, which anyone reproducing from the artifacts will walk into; and print numbering of figures and tables is unverified, because the machine on which the corrections were made has neither pandoc nor pdflatex. The models named here will be superseded within months, and the plans, harness, scoring code and per-cell artifacts are released so the evaluation can be re-run rather than the recommendation trusted. <!-- addresses: R3.preamble, C2, R3.3, R3.5, R3.6, R3.7, R2.9, R2.6, R3.13, R3.14, T3.1, T3.2, T3.5, T3.7 -->

### Conclusion

Across two workflow classes, two infrastructures and two execution modes, the specification and not the model determined whether a free local executor succeeded. A model generation newer than the experiment reproduced the same requirement for literal syntax; a plan corrected eleven times, and not a change of model, is what produced a clean run on a production server; and where the plan was thin, no amount of additional reasoning recovered the result. For a laboratory the practical reading is that the model is a commodity and the plan is the asset. At the task sizes measured here the reasons to run an executor locally are data governance and freedom from per-call metering, not cost. <!-- addresses: R3.15, R3.13 -->

### Prompt structure for the planner and the executor

Both prompt files are reproduced verbatim below the tables (`prompts/system.txt`, `prompts/track_a_user.tmpl`, `prompts/track_b_user.tmpl`). Their structure, by category, is as follows.

The **system prompt** fixes the role ("an expert bioinformatician") and the output contract (one self-contained bash script, no prose, no markdown fences), then imposes seven hard constraints on the emitted script: the shebang line, `set -euo pipefail`, an assumed working directory containing `data/raw/` and `data/ref/`, all output under `results/`, idempotency on re-run, no absolute paths outside the working directory, use of only the tools in the injected inventory with no package managers, and a 600 s wall-clock ceiling at four threads. Three of these are enforced by the harness — the wall-clock kill, the tool inventory on `PATH`, and the working directory. The rest are requests the model can violate, and the Methods say so.

The **user template** has five slots in a fixed order: the task specification (per-sample variant calling on four paired-end samples, with the exact list of required output paths and the exact column header of the collapsed table); the dataset manifest, naming every input file; the tool inventory, injected at run time from `setup/verify_env.sh` so the prompt cannot drift from the environment; the plan slot; and the output-format reminder. Track A and Track B differ only in the plan slot: Track A substitutes the plan file, Track B substitutes the sentence "None provided. Design and implement the workflow yourself, using only the tools above." Because the Track B template contains no plan placeholder, every Track B run is a no-plan run regardless of which plan file was nominally passed to the harness — a rule that must be honoured in any re-analysis of the released data.

Safety and validation checks are carried by exactly one plan condition. `v2_defensive` adds a `try()` helper, per-step validation, retry-once semantics, a `failures.log`, and an exit-code policy. The other seven plan files carry none of these. That difference is a measured experimental condition, not an oversight, and it is the comparison from which the claim that a defensive plan changes error handling for a local and a frontier executor alike is drawn.

The **Galaxy planner** is structured differently, because the executor there is a loop rather than a single generation. The plan is a router: a 50-line `PLAN.md` index plus seven step files, so that the model loads only the step it is currently executing and its context does not accumulate the whole plan. The seventh file is the verification step, and it is reproduced twice in the Supplement: the deployed version, which states no expected values, requires a dataset identifier beside every reported number, and sanctions `UNAVAILABLE` as an answer; and the original version, which stated its own expected values ("~5,594 genes, ~92% assigned") and would therefore let an executor that never opened a dataset produce a flawless verification by recitation. The pair is shown side by side because the general point applies beyond this study: any agent evaluation that places the expected answer in the task description cannot distinguish execution from recitation. <!-- addresses: R1.4, R1.1 -->
